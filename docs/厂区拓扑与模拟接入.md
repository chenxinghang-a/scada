# 厂区拓扑与模拟设备接入

> 解决两件事：① 拓扑图「乱成一坨」；② 模拟设备「太少太假、接不进接不出」。

---

## 一、拓扑为什么是「一坨」

原来的拓扑数据源是 `模板/industry40.html` 里的一张硬编码表：

```javascript
var TWIN_DEVICE_MAP = {
    'siemens_1500_01': { label: '锅炉产线', icon: '🔥', x: 30,  y: 60, ... },
    'hollysys_lk_01':  { label: '化工车间', icon: '⚗️', x: 200, y: 20, ... },
    ...
};   // 一共 7 台，坐标手填像素值
```

问题不是「画得不好看」，是**数据源和现实脱节**：

| 现象 | 原因 |
|---|---|
| 42 台设备里只有 7 台在图上 | 表里只写了 7 台 |
| 其余设备按 id 字母序平铺、夹杂车间名 | 另一处渲染按 `devices` 数组顺序遍历，`zone` 字段散落在 15 种叫法里 |
| 「产线设备拓扑一样」 | 7 个节点被复制到每条线上，没有真实的工序列 |
| 设备改名 / 扩容后图失真，**没有任何报错** | 硬编码表不会因为配置变了而报错 |

**根本原因：坐标和层级写在前端，而不是从配置来。**

## 二、新结构：配置驱动，后端算坐标

```
配置/topology.yaml            厂区骨架：车间 → 产线 → 工序顺序
配置/devices_simulated.yaml   设备：workshop / line / stage / role
        ↓
展示层/api/api_devices.py     GET /api/devices/topology（算布局）
        ↓
模板/industry40.html          只负责画（不再有任何坐标常量）
```

### 2.1 设备上的四个层级字段

```yaml
- id: injection_m1
  name: 注塑机1# (海天MA2100)
  site: east_plant          # 厂区
  workshop: injection       # 车间（id）
  zone: 注塑车间             # 车间（中文名，旧代码还在读）
  line: injection_a         # 产线
  stage: 注塑               # 工序（决定拓扑图从左到右的列）
  role: equipment           # equipment / instrument / controller
```

`role` 决定**画在哪一层**：

| role | 含义 | 画在哪 |
|---|---|---|
| `equipment` | 工艺设备（注塑机、泵、炉） | 上层流水线，参与物料流箭头 |
| `instrument` | 旁路仪表（变送器、流量计） | 同列下方，不参与物料流 |
| `controller` | PLC / DCS / 服务器 | **底部单独一行**，虚线框 |

> 为什么控制器要单独一行：PLC 和设备画在同一列时，图上会出现
> 「干燥机 → 西门子S7-1500 → 注塑机」——中间那个箭头物理上不存在。
> 现场看板的标准画法是「上面一条工艺流水线，下面一条控制层总线」。

### 2.2 布局算法（后端算，前端只画）

```
列  = 工序（topology.yaml 里 stages 的顺序）
行  = 同一工序内的设备（equipment 在上、instrument 在下）
坐标 = PAD + col × (NODE_W + GAP_X)
```

- 空工序列**跳过并重新编号**（否则图上出现一段空白，看起来像「这里应该有设备但没有」）
- 没写 `stage` 的设备挂到最后一列，**不丢弃**（丢了就是「设备存在但图上找不到」）
- 连线只连相邻工序的 `equipment`：下游 1 台则多对一汇聚，上游 1 台则一对多分发，否则按索引配对

### 2.3 接口返回

```json

  "summary": {"workshops": 14, "lines": 34, "devices": 129,
```

## 三、模拟设备：从 42 台到 129 台

### 3.1 为什么用「模板 + 生成器」而不是手写

手写 42 台还行，写到 129 台必然出错（地址撞车、量纲写错、单位缺失、模拟参数漏配），
而且每加一台要同步改两个文件。

```
配置/device_templates.yaml   设备族 → 点位结构（20 个模板）
tools/gen_factory.py         厂区布局 → 哪台设备、在哪个工序
配置/devices_simulated.yaml  生成结果（现场可读可改）
```

20 个模板覆盖：旋转机械、热工设备、储罐、换热器、机床、机器人、输送线、
包装机械、电气柜、计量仪表、反应釜、塔器、分析仪、注塑机、干燥机、模温机、
堆垛机、充电桩、服务器、安全设备。

**同型号设备不会读出一模一样的数字**：每台设备的 `base_*` 按 id 的 sha256
做 ±6% 稳定偏移（模拟设备老化/安装差异）。用 sha256 不用 `hash()`——
后者有随机化种子，每次进程启动结果不同，历史曲线会出现无法解释的台阶。

## 四、模拟「正常接入接出」：真实协议线

### 4.1 问题

原来的模拟模式是**进程内假客户端**（`EnhancedSimulatedModbusClient` 直接返回数值），
没有任何协议报文经过。后果：

- float32 字节序、32 位寄存器拼接、JSON 路径这些最容易错的地方**从没被验证过**
- 改一个点位地址，模拟照常出数（因为它根本不看地址），现场却读不到
- 「能读不能写」只能到现场才发现

### 4.2 新架构

```
模拟服务端/                      采集层/
├── device_data_hub.py    ────→  真实客户端（pymodbus / asyncua / requests / paho）
│   复用 DeviceBehaviorSimulator       ↑ 真实协议报文
├── modbus_slave_pool.py        ──────┘
├── opcua_server.py
├── rest_gateway.py
├── mqtt_broker.py
└── server_main.py        统一入口（start_all / stop_all）
```

```bash
# 独立跑服务端
python -m 模拟服务端.server_main

# 应用内嵌跑（起服务端 + 用真实客户端采集）
python run.py --sim-live
```

端口不另算 —— 每台设备的 `sim_endpoint.port` 由生成器写进配置，
服务端和采集层读**同一份配置**：

```yaml
- id: injection_m1
  host: 192.168.1.1          # 现场地址
  port: 502
  sim_endpoint:              # 模拟服务端监听地址
    host: 127.0.0.1
    port: 15021
```

切现场只改 `host`/`port`，代码一行不动。

### 4.3 服务端分工

| 服务端 | 端口 | 说明 |
|---|---|---|
| Modbus TCP 从站池 | 15020+ | **每台设备一个真从站**（模拟「一台设备一个 IP:502」），数据块直接委托给 hub |
| OPC UA Server | 15400 | 一个 Server 承载 3 台设备 / 28 个点位，**namespace 与配置的 node_id 对齐** |
| REST 网关 | 15500+ | 每台设备一个 HTTP 网关，按 `endpoints[].json_path` **反向构造嵌套 JSON** |
| MQTT Broker | 18830 | 自写的最小 MQTT 3.1.1 broker（零依赖），支持通配符订阅与 retained |

### 4.4 两个必须踩过的坑

**① OPC UA 的 namespace 不能硬编码**

真实设备的 NodeId 是厂家定死的（`ns=3;s=Temperature`）。如果模拟服务端自己分配
一个 ns 并生成 `ns=2;s=opcua_plc_01.Temperature`，那配置里的 node_id 永远是错的 ——
现场抄来的地址在模拟环境里连不上，模拟环境里跑通的到现场又是错的。

所以服务端**服从配置**：配置写 ns=3，服务端就把 index 3 准备好。

但 asyncua 的 `Server()` 自己会先注册一个 namespace（index 1），
直接按 1..N 顺序注册会**整体偏移一位**（配置要 ns=3、实际建成 ns=4），
而日志里只看到「映射 {1:2, 2:3, 3:4}」—— 一眼看不出偏了。

正确做法：先读当前 namespace 表算下一个可用 index，只在 `next == want` 时注册。

**② Modbus RTU 设备要当 TCP 连**

`modbus_rtu` 的真实客户端会去开串口，报
`Serial client requires pyserial` —— 一个和模拟服务端完全无关的错。
模拟服务端用 TCP 从站承载 RTU 设备（现场也常这样：串口服务器把 RTU 转成 TCP），
所以 live 模式下要把 `protocol` 临时改成 `modbus_tcp`。

### 4.5 验证：`tools/sim_live_selftest.py`

```bash
python tools/sim_live_selftest.py              # 21 项
python tools/sim_live_selftest.py --only modbus
```

| 检查 | 结果 |
|---|---|
| 数据中枢启动 | 129 台 |
| 连接成功率 | **129/129**，耗时 0.9s |
| Modbus 点位值与服务端一致（含字节序） | 3 台 × 6 点位 ✅ |
| Modbus 写入回流到数据中枢 | ✅ |
| OPC UA 订阅（node_id / 12 点位） | 2 台 ✅ |
| REST 端点值量纲正确 | 2 台 × 10 端点 ✅ |
| MQTT 消息接收 | 2 台 ✅ |

**比对口径说明**：Modbus 是主动读，读到的就是当前值，做**精确比对**（2% 容差）；
OPC UA / REST / MQTT 是推送/轮询缓存，客户端手里是「上一次」的值、服务端快照是
「当前 tick」，慢变量天然差一截 —— 只做**量纲比对**（50% 容差），
抓「JSON 路径错拿到 None」「量纲差 10 倍」「topic 不匹配」这类真问题。

## 五、日常操作

### 加一台设备

```bash
# 1. 在 tools/gen_factory.py 的 NEW_DEVICES 里加一条
# 2. 重新生成（--force 会用模板重刷模板设备，手工维护的 42 台不动）
python tools/gen_factory.py --force
# 3. 体检
python tools/sim_probe.py --gaps          # 缺值必须为 0
python tools/site_checkup.py              # 上线前检查
```

### 改产线工序顺序

改 `配置/topology.yaml` 的 `stages` 列表，刷新页面即可。不用重启服务（拓扑接口实时读文件）。

### 让某台设备不参与物料流

把它标成 `role: instrument`（旁路仪表）或 `role: controller`（控制器），
拓扑图会自动把它移出流水线箭头。

## 六、已知限制

| 限制 | 说明 |
|---|---|
| MQTT 采集按 payload 的 key 当点位名 | 配置里 `topics[].name` 被忽略（采集层既有行为）。模拟服务端按 `name` 发 key，所以能对上；接真实 MQTT 设备时如果 payload 的 key 和配置的 name 不同，需要改采集层 |
| OPC UA 只支持无安全策略 | 模拟服务端没配证书。现场如果要求 `Basic256Sha256` + 用户名密码，需要给服务端加证书 |
| 129 台设备的 Modbus 从站占 100 个端口 | 本机没问题，但某些受限环境可能端口不够。需要时可改成「一个端口 + 多 unit id」 |
| 拓扑图一次返回全部 129 台 | 单次响应约 200KB。设备数再翻倍时要加分页或按车间懒加载 |
