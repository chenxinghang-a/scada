# 审计：监控数据链路与可视化

> 范围：`展示层/api/*`、`展示层/websocket.py`、`存储层/database.py`、`采集层/data_collector.py`、`静态资源/js/*`、`模板/*.html`。
> 前端主仓库 `scada-app` 不在本机，本报告只依据本仓库内的后端契约与静态资源实现。

## 一、结论

后端其实**采集了**能判断「旧/坏/离线」的三样东西——`timestamp`（采集时刻，非入库时刻）、`quality`（OPC UA 码）、`created_at`（入库时刻）——但这条信息链在**推送和展示两级都断了**：推送线程不做陈旧闸门，前端不读时间戳。结果是运维屏幕上**只有一个维度**：`connected` 布尔值驱动的「运行中/离线」标签，而这个标签和值本身互不联动——离线设备的数值照样以正常样式、绿色质量点显示在卡片上。更糟的是趋势图的 X 轴取的是**浏览器时钟**而不是数据时间戳，PLC 断线 5 分钟后曲线仍然每秒往前画，这是最典型的「假实时」。告警侧则是反方向的错误：已恢复的报警不筛 `cleared`，一条两小时前就恢复的报警会让设备卡永久挂红框。**当前状态：不能一眼看出哪里不对。**

## 三、接口契约现状

| 接口 | 实际返回字段（读自代码） | 缺失 / 问题 |
|---|---|---|
| `GET /api/data/realtime` | `data[]`：`id`, `device_id`, `register_name`, `value`, `unit`, `timestamp`（采集时刻）, `created_at`（入库时刻）, `quality`（OPC UA 码，默认 192）<br>参数：`device_id`、`limit`(≤10000) | 缺 `stale` 标记、缺设备在线态（客户端要再拉一次 `/api/system/status` 做 join）、缺 `data_type`/`scale`、无分页/无多设备过滤。`timestamp` 是 naive 字符串 |
| `GET /api/devices` | `devices[]`：`device_id`, `id`, `name`, `description`, `protocol`, `host`, `port`, `enabled`, `connected`, `stopped`, `device_category`, `registers[]`, `nodes[]`, `topics[]`, `endpoints[]`, `stats{}` | 缺 `last_seen` / `data_age` / `stale`。⚠️ 该 GET 会**触发自动重连**（`采集层/device_manager.py:587-594`），是带副作用的查询 |
| `GET /api/alarms/active` | `alarms[]`：`alarm_id`, `device_id`, `register_name`, `alarm_level`, `alarm_message`, `first_trigger_time`, `last_trigger_time`, `trigger_count`, `sample_count`, `acknowledged`, `shelved`, `pending` | 缺 `actual_value` / `threshold` / `unit`（WS `alarm` 事件里有）、缺 `cleared`（内存态本就不含恢复项，但字段语义应与 `/api/alarms` 对齐） |
| `GET /api/alarms` | `SELECT *`：含 `threshold`, `actual_value`, `last_value`, `trigger_count`, `acknowledged`, `acknowledged_at`, `cleared`, `cleared_at`, `timestamp`, `last_trigger_time` | **无 `cleared` 过滤参数**，默认返回已恢复记录；前端也没筛 |
| `GET /api/data/history/<dev>/<reg>` | 原始（`interval=''`）：`timestamp`, `value`, `unit`<br>聚合（`1min/5min/1hour/1day`）：`time_bucket`, `avg_value`, `min_value`, `max_value`, `sample_count`<br>响应外层另有 `truncated` | 聚合分支**没有 `unit`**；两条分支都**没有 `quality`**；`5min` 分支的 `time_bucket` 格式与其它分支不一致（`database.py:991-1005`） |
| `GET /api/trend/*` | **不存在** | 任务书里假设的趋势接口在本仓库没有实现；前端趋势图（`dashboard.js:1027`）压根不查历史，只用浏览器内存缓冲 |

## 四、建议修复顺序

1. **先修「假实时」三件套（P0 #1/#4/#5）**——改动小、风险低、直接决定运维信不信这块屏：趋势图换用 `timestamp`；推送线程加陈旧闸门；前端显示「x 秒前」。
2. **再修两个「反向误导」（P0 #2/#3）**——已恢复报警必须从设备卡上消失；解码失败必须留一个 BAD 占位而不是让点位「人间蒸发」。这两条修完，界面上的红/绿才可信。
3. **打通质量位到历史（P1 #10/#9/#8）**——`history_data` 加 `quality`、报警列表补 `cleared`/`cleared_at`/`actual_value`/`threshold`，让事后复盘和现场判断用同一套数据。
4. **补实时推送（P1 #6）**——加解压或关压缩。这条不修，前三条在 WS 通道上等于白做（39/42 台设备的推送根本没到前端）。
5. **最后做体验与性能（P2 #14-22）**——精度、量程、分页、增量推送、背压、组态图，按运维实际抱怨排序，不要一次性重构。
