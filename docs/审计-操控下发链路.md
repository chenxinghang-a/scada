# 审计：操控指令下发链路

审计范围：`智能层/device_control.py`、`采集层/real_device_manager.py`、`展示层/api/api_control.py`、`展示层/api/api_devices.py`、`采集层/modbus_client.py`、`用户层/auth.py`、`模板/control.html`。只读审计，未改动任何代码。

## 一、结论

不能可靠下发。**只有 `write-register` / `write-coil` 这一条路径的闸门是齐的**（急停/联锁/量程/审计/回读/类型六项都在），但它的回读读的是客户端缓存：通信一断，旧值会被当成回读结果，于是"写了报未生效"与"没读到报验证通过"两种假结论都会出现；写超时时异常直接抛成 500，审计里只留 `write_attempt` 没有结果，事后无法回答"到底执行了没有"。

更要紧的是**设备启停与参数调节是另一条完全敞开的写路径**：不经 `device_control`、无急停、无联锁、无审计、无回读、`int()` 静默截断——闸门只装在操作员最常点的那个页面上。

前提说明：随仓库发布的 `配置/devices.yaml` **没有任何 `write_limits`**（全库 0 处），真实模式下 `validate_write` 一律拒绝，故回读类缺陷要等量程配置补全后才暴露。这不构成免责——配置补全是迟早的事，届时不会有任何代码变更提醒。

## 三、两条写路径的逐项对照表

| 校验项 | `device_control.write_with_verification`（API 写寄存器/线圈） | `real_device_manager` 启停/调节（设备管理入口） |
|---|---|---|
| 急停检查 | ✅ `:1587`，且拿锁后复核 `:2164` | ❌ 无（`_estop_active` 字段存在但启停/调节都不读） |
| 联锁检查 | ✅ `:1578` 无规则即拒 + `:1654` 阻止检查 | ❌ 无 |
| 量程校验 | ✅ `:1600-1651`，无 `write_limits` 真实模式即拒 | ❌ 无（`adjust_device` 仅判 `access == 'ro'`） |
| 审计 | ✅ attempt→ok/failed 三态 + 哈希链，审计失败即拒写 `:2180` | ❌ 无（仅 `api_devices` 成功后写一条 auth 操作日志，失败不记） |
| 回读验证 | ⚠️ 有 `:2260-2286`，但读缓存、不判新鲜度（见缺陷 3） | ❌ 无，`bool(write_single_*)` 即成功 |
| 类型严格性 | ✅ `kind` 必填、拒绝非整数 `:2218-2236` | ❌ 无，`int(value)` 静默截断 |
| 设备操作锁 | ✅ `:2146` | ❌ 无 |

补充：`batch_control` 是第三条内联写路径（`智能层/device_control.py:780-789`），有急停与联锁、有审计，但**无量程、无回读**；联锁动作（`:1439`）按设计不受操作员闸门约束，但缺回读。

## 四、建议修复顺序

1. **先堵后门**（缺陷 1、2）：`/devices/{id}/start|stop|adjust` 三个入口收敛到 `device_control`。这是唯一"急停期间仍能写 PLC"的通道，改动面也最小。
2. **再修回读语义**（缺陷 3、4）：回读判 `last_read_source`，写异常必须落 `write_failed` 并返回可区分的错误码。这两条决定"能不能回答执行了没有"，是本次审计的核心问题。
3. **失败语义分层**（缺陷 5、6、7）：403/504/503/409 分开；`validate_write` 加 `kind`；批量去掉二次下发并补回读。
4. **前端不再自欺**（缺陷 8、9、13）：三态显示、去掉 `parseInt`、失败文案如实。
5. **可追溯性**（缺陷 10-12、14-16）：幂等键去 value、审计回载、联锁回读、越权留痕、权限统一。
