# 上线前验收清单

> 这份清单回答一个问题：**「现在这套东西，能不能真的用？」**
>
> 与 `tools/site_checkup.py` 的分工：体检查的是「配置/依赖/目录」这些**静态条件**；
> 本清单查的是「服务跑起来之后**行为**对不对」。两者互补，都要过。

每一节都是**可复制粘贴的命令 + 明确的预期输出**。全部只读，不改任何数据。

---

## 〇、前置

```bash
cd <仓库根目录>
.venv/Scripts/activate          # Windows；Linux 用 source .venv/bin/activate
python -m pytest -q             # 约 23 分钟
```

**预期**：`4528 passed, 11 skipped`，0 failed。

> ⚠️ 这一条**不能替代**下面任何一节。全量测试覆盖不到「装配」和「渲染」——
> `run.py` 的启动路径、模板的实际渲染、前端资源加载，都没有 pytest 覆盖。
> 下面的 1–4 节才是真正证明「能用」的部分。

## 一、服务能不能启动

```bash
python run.py
```

**预期**（约 30–40 秒；库里历史多时会到 1 分钟以上）：

```
数据采集器已启动，共 129 个设备 (mqtt:2, rest:8, modbus_tcp:100, opcua:3, modbus_rtu:16)
预测性维护后台分析已启动
OEE计算器已启动
能源管理已启动
边缘决策引擎已启动
振动分析器已启动
启动Web服务...
工业数据采集与监控系统已启动
```

**允许出现的 WARNING**：
- `TDengine连接失败，跳过TDengine集成` —— TDengine 是可选组件（见 §五）
- `系统降级项: ['device_freshness', 'memory']` —— 冷启动时无数据，属正常

**不允许出现**：
- `ERROR` 且重复刷屏（单条 TDengine/REST 连接失败除外）
- `Traceback`

> 启动慢的解释：首次启动会跑一次数据保留策略（清历史），
> 库里 200 万条时约 56 秒。**第二次启动是快的**（10 秒级），因为已经清过了。
> 这不是缺陷，不用去优化启动代码。

## 二、接口能不能响应

另开一个终端：

```bash
python -c "
import requests
p={'http':None,'https':None}
for u in ('/api/health/status','/api/devices'):
    r=requests.get('http://127.0.0.1:5000'+u,timeout=5,proxies=p)
    print(u, r.status_code, r.text[:100])
"
```

**预期**：

| 路径 | 状态码 | 说明 |
|---|---|---|
| `/api/health/status` | `200` | `{"data":{"global_status":"degraded","version":"1.3.xxxx"},...}` |
| `/api/devices` | `401` | `{"code":"NO_TOKEN",...}` —— **401 是对的**，说明认证生效 |

> `global_status: degraded` 在没装 TDengine 时是常态，不是故障。
> 判断「是否有问题」看的是 `unhealthy` 模块，不是这个字段。

## 三、登录后能不能拿到真实数据

```bash
python -c "
import requests
p={'http':None,'https':None}
B='http://127.0.0.1:5000'
t=requests.post(B+'/api/auth/login',json={'username':'admin','password':'admin123'},timeout=8,proxies=p).json()
tok=(t.get('data') or {}).get('token') or t.get('token')
H={'Authorization':'Bearer '+tok}
for u in ('/api/devices','/api/alarms/active','/api/devices/topology'):
    r=requests.get(B+u,headers=H,timeout=10,proxies=p)
    print(u, r.status_code, r.text[:120])
"
```

**预期**：

| 路径 | 状态码 | 关键内容 |
|---|---|---|
| `/api/devices` | `200` | 设备列表，含 `connected: true` |
| `/api/alarms/active` | `200` | `{"alarms":[]}`（无活跃报警） |
| `/api/devices/topology` | `200` | `summary.devices = 129`，`site.name` 有值 |

**三条一致性检查**（最容易出问题的地方）：

1. `topology.summary.devices` == 启动日志「共 N 个设备」 == `配置/devices_*.yaml` 条数
2. `devices` 列表长度 == 同上
3. 拓扑里每台设备都能在设备列表里找到（没有「图上有、列表没有」的幽灵节点）

## 五、可选组件缺位时必须降级，不能阻断

TDengine 是可选组件。**不装它，服务也必须能正常启动**。

已验证的行为：

```
ERROR | tdengine_client | REST API异常: ... 由于目标计算机积极拒绝
WARNING | run | TDengine连接失败，跳过TDengine集成
```

- `ERROR` 一条（记录连接失败）+ `WARNING` 降级，**可以接受**；
- 服务继续启动、接口照常响应；
- `health/status` 里 `global_status` 会显示 `degraded`。

**如果 TDengine 连不上导致服务起不来 —— 那是缺陷，不是配置问题。**

> ⚠️ 注意：TDengine 的 REST 请求必须显式关代理
> （`proxies={'http': None, 'https': None}`）。
> 开发机和不少现场服务器都配了 `HTTP_PROXY`，不关的话连 `localhost:6041`
> 都会走代理，报 `ProxyError`，看起来像时序库挂了。

## 六、已知限制（不是缺陷，别当 bug 修）

| 现象 | 原因 | 处理 |
|---|---|---|
| 首次启动 30–60 秒 | 数据保留策略首次执行，清历史 | 等；之后重启 10 秒级 |
| `global_status: degraded` | TDengine 未装 / 冷启动无数据 | 正常 |
| `/api/*` 返回 401 | 认证生效 | 带 `Authorization: Bearer <token>` |
| 页面访问被重定向到登录页 | 页面级认证 | 先登录（cookie `token`） |
| 拓扑里设备数 ≠ 配置数 | 配置改了但服务没重启 | 重启；或查 `topology.yaml` 与 `devices_*.yaml` 是否一致 |

## 七、这份清单本身的维护

每条断言都对应一个**真实踩过的坑**：

| 节 | 对应的坑 |
|---|---|
| §一 | 曾把「连接被拒」当成应用起不来，实际只是启动要 40 秒 |
| §二 | 曾把 `degraded` 当成故障，实际是可选组件缺位 |
| §三 | 曾出现「拓扑 129 台、设备列表 0 台」这种口径不一致 |
| §四.3 | 曾只验 HTML 不验渲染，模板错位时 `200` 照样返回 |
| §五 | 曾有本地请求走系统代理，报成「时序库挂了」 |

**改这份清单时**：新增一条断言，就要能说清它防的是哪个具体现象；
说不清的不要加 —— 假红会训练人忽视整份清单。
