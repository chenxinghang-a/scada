# 审计：异常场景与降级行为

> 审计对象：`industrial_scada`（Python/Flask）工作区当前状态（含 round 341 未提交改动）。
> 方法：只读源码，逐场景追踪「异常 → 降级 → 可观测性」三要素。**未修改任何代码。**
>
> 变更归属说明：缺陷 #3 涉及的 `采集层/device_manager.py`、`real_device_manager.py`、`simulated_device_manager.py` 三处 `ConfigManager.load_yaml` 改动是**工作区未提交改动（M 状态），非本次审计所加，也非本轮任何一位审计员所加**——提交前需要认领。

## 一、结论

出异常时系统**大部分场景可预期，但关键路径上仍有七处会「静默继续」**——失败被计成成功、旧值被当成新值、配置没生效却被当成已生效。

好的一面：写操作主链路（`write_with_verification`）已做到拿锁后复核、执行前落审计、审计失败即拒写；采集队列先落盘再入队，崩溃可恢复；采集中断有独立的 30s 看门狗报警；设备/联锁/能源三处的 mtime 基线与「同一坏文件不刷日志」纪律是对的。这些是正确形态。

坏的一面：**「静默继续」仍集中在采集侧与两条被遗忘的路径上**——REST 设备全读失败仍被计为成功（熔断器永不打开）、MQTT retained 旧值被盖上 `now()` 当实时值入库、设备真掉线时既没有离线告警也没有进入安全状态（`update_device_health` 零调用方）、PID 闭环这条写路径绕过急停/联锁/审计、设备配置热重载在生产里**根本不存在**（`reload_config` 只定义在从未实例化的基类上）。

**最严重的不一致**：三处「配置热重载」对外都说支持，实际是三种不同结局——`devices.yaml` 压根没实现（`AttributeError` 被吞成「重载异常」，接口回「可能有语法错误」）、`interlocks.yaml` 先把规则清空再加载（一次编辑器中间态保存即让全部联锁消失）、只有 `energy.yaml` 是真正的 fail-closed。同一个「改配置」动作，三种信任度。

## 四、建议修复顺序

1. **#1 联锁热重载**（安全功能可被一次保存静默清空，且与 devices 的 fail-closed 直接矛盾——本轮「不一致」主题的最强样本）。改法可整段照抄 `device_manager.reload_config`。
2. **#7 设备热重载不存在**（与 #1 是同一件事的两半：联锁热重载会毁掉规则，设备热重载压根没实现。`reload_config` 上移到接口即可，改完 #1 才有「保留旧表」这个参照实现可用）。
3. **#2 PID 写路径**（唯一还在绕过急停/联锁/审计的写通道，且失败静默；`/adjust`、`/start`、`/stop` 已在 round 341 收敛，只剩这一条）。
4. **#3 配置解析退化**（工作区未提交改动引入的回归；三种输入都会变成「服务看起来正常但一台设备都不采」，其中 `PermissionError`/GBK 编码这类"文件看着是好的"最难查）。
5. **#4 + #6 采集失败可观测性**（REST 恒成功 + 离线无告警，是同一条链上的两个断点；#4 修好后 `failed_collections` 才有意义，#6 才能接上）。
6. **#5 MQTT retained**（与 #4 同属「旧值当新值」，改动面小，顺手做掉）。
7. **#8 审计一致性**（把 `log_operation` 收口到带返回值的 `_audit`，一次改动消除一整类不一致）。
8. **#9 联锁去抖**（安全动作误触发代价高，但改动会引入确认延迟，需要和现场确认 N 值与质量码策略后再动）。
9. #10~#19 按现场抱怨排序，其中 #12（池耗尽）建议在设备数超过 20 台前处理，#19（测试假绿）建议与 #7 同批改，否则修完还会绿着。
