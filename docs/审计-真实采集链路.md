# 审计：真实设备采集链路

审计范围：`run.py --real` → `RealDeviceManager` → 各协议客户端 → `DataCollector`。只读代码，未改动任何文件。

> **审计后变更（2026-11-03）**：本文提交后，共享工作区里 `采集层/real_device_manager.py`、`simulated_device_manager.py`、`device_manager.py` 的配置加载已被他人改为 `ConfigManager.load_yaml(...)`。因此下文 **P0 #1（`${VAR}` 不展开）在当前工作区已不成立**，行号也已偏移（`real_device_manager.py:100`）。
> 该改动同时引入一个新的 P0 回归：`ConfigManager.load_yaml` 在 YAML 解析失败时 `except` 后 `return {}`（`core/config_manager.py:113-115`），使 `device_manager.py:187-222` 的 `_load_config_into()` 对"写坏的配置"返回 **True** 并让 `load_config()` 用空表覆盖 → 服务正常启动、0 台设备、无告警，round 284 的 fail-closed 守卫在启动路径失效（已实测：坏 YAML 下 `load_config()` 返回 True、设备数 0）。修复建议见该文件对应条目，结论：这三个 manager 应改用 `yaml.safe_load` + `config_manager.expand_env_vars`（已实测：解析失败抛 `ParserError`，`${VAR}` 仍能展开）。

## 一、结论

**真实模式目前不可用。** `devices_real.yaml` 里仅有的两台示例设备都跑不通：PLC 的 `host` 是未展开的 `${PLC_HOST_01}` 字面量，MQTT 的 `topics` 写成字符串列表会被静默跳过（零订阅、零数据）。REST 设备一旦网关不可达，请求无超时会永久占用采集线程池；任一设备配置非法（如 `byte_order` 写错）会让 `connect_all` 抛出，连带整个采集器不启动，而 Web 服务照常显示"启动成功"。

唯一相对可信的是 Modbus 轮询链路：字节序、`scale/offset`、陈旧缓存标记与质量码降级都真的接上了。MQTT/OPC UA/REST 三条链路则是"能连上但数据不可信"——点位名、`json_path`、质量码、时间戳四处失真。另有一条与协议无关的硬伤：**设备配置热重载在生产里根本不存在**（两个生产类都没有 `reload_config`），现场改一次点位只能重启进程，而手动接口会回一句误导性的"配置文件可能有语法错误"。

## 三、逐项证据（P0）

> 编号在修复顺序里被引用，故未随优先级调整而重排；#15 原列 P2，经与 `docs/审计-异常场景降级.md` 缺陷 #7 交叉核对后上调为 P0（两处入口全断 + 手动接口回误导性 400）。
> **去重口径**：#15 与 `docs/审计-异常场景降级.md` 的 #7 / #19 是同一缺陷，**主文档记那一份**（含 API 路径与"测试假绿"），本文只保留采集侧与维护任务视角；汇总按一条计。两份文档范围不同（那份含联锁/energy/启停），**P0 数不可相加**。

**#1 环境变量不展开。**（审计时的状态；当前工作区已改为 `load_yaml`，见文首注）`RealDeviceManager` 直接用 `yaml.safe_load`，而展开逻辑只存在于另一条加载链：

```python
# 采集层/real_device_manager.py:92-93
with open(config_file, 'r', encoding='utf-8') as f:
    config = yaml.safe_load(f)          # 无 expand_env_vars
# core/config_manager.py:101-102（未被调用）
config = expand_env_vars(config, _source=config_path)
```

`config.py:15` 的 `load_dotenv()` 已把 `.env` 灌进 `os.environ`（含 `PLC_HOST_01`），但没人去替换。`ModbusTcpClient(host="${PLC_HOST_01}")` 必然 DNS 失败，日志只说"连接失败"。

**#2 MQTT 字符串 topics 被丢弃。** `devices_real.yaml:72-74` 是字符串列表，真实客户端只认 dict：

```python
# 采集层/mqtt_client.py:216-219
for topic_config in self.topics_config or []:
    if not isinstance(topic_config, dict):
        logger.warning(f"无法识别的 topic 配置（已跳过）: {topic_config!r}")
        continue
```

结果 `_subscriptions` 为空 → `_on_connect` 里 `for topic, qos in self._subscriptions.items()` 一次都不执行 → 连接成功但永不订阅。模拟客户端（`simulated_client.py:939`）恰恰按 dict 的 `name` 造数据，所以模拟模式毫无症状。

**#3 REST 超时不生效。** `requests.Session` 没有 `timeout` 属性，`Session.request` 总是显式传 `timeout=None`（本机 requests 2.34.2 已实测：`__attrs__` 不含 `timeout`，`send()` 只 `setdefault` stream/verify/cert）：

```python
# 采集层/rest_client.py:140
self._session.timeout = (3, 5)     # 无效属性，requests 从不读
# 采集层/rest_client.py:203-208
resp = self._session.request(method=method, url=url, ...)   # 未传 timeout
```

网关断电 → `recv` 永久阻塞。`_handle_normal_collection` 的 `future.result(timeout=30)` 虽会超时返回，但线程本身不退出，20 个池线程被逐个占满后，所有设备（含 Modbus）都排不上队。

**#4 一台坏配置打断整条启动链。** `connect_all` 内无异常隔离，`ModbusClient.__init__` 会抛：

```python
# 采集层/modbus_client.py:73
self.byte_order = ByteOrder(config.get('byte_order', 'ABCD').upper())  # 非法值 -> ValueError
# run.py:579-585
connection_results = device_manager.connect_all(timeout=20)   # 异常直接冒出
device_manager.start_reconnect_loop(interval=30)              # 不再执行
...
_apply_ha_role(ha_manager.role)                               # data_collector.start() 不再执行
```

`run.py:633` 捕获后只写 `app.background_start_error`，Web 正常对外服务。现场看到的是"系统起来了、所有设备离线、没有任何数据"，而根因藏在一行 ERROR 日志里。

**#15 热重载的两条入口都断，且报错误导。** `reload_config()` 只存在于基类，两个生产类都没有：

```python
# 采集层/device_manager.py:246  ← 唯一实现；但 DeviceManager 生产侧零实例化
def reload_config(self, allow_empty: bool = False) -> dict[str, Any]:
# 展示层/api/api_devices.py:244-249
try:
    diff = device_manager.reload_config() or {}
except Exception as e:
    return jsonify({'success': False,
        'message': f'设备配置重载失败（配置文件可能有语法错误）: {e}'}), 400
```

实际回给运维的是 `…可能有语法错误: 'RealDeviceManager' object has no attribute 'reload_config'`——把"方法不存在"包装成"配置写错了"。`tests/test_device_config_reload.py:258-266` 用 `DeviceManager`、`281/304` 用 `MagicMock`，所以功能全废而测试全绿。

## 四、建议的修复顺序

1. **先让"能连上"成立**（#1 #2 #4）：加载器改成 `yaml.safe_load` + `expand_env_vars`（保留"解析失败必须抛"的契约）；MQTT topics 兼容字符串；`connect_all` 逐台隔离异常。这三条不修，真实模式 100% 不可用。
2. **再堵住"卡死"**（#3）：REST 显式传 `timeout`，并给 `_handle_normal_collection` 加"线程超时即判失败并重建客户端"的兜底。
3. **再修"数据可信"**（#5 #6 #7 #8 #9 #14）：点位映射、失败计数、时间戳透传、质量码透传、报警只吃 GOOD。这一组决定系统敢不敢用来做判断。
4. **修"改配置能生效"**（#15）：`reload_config` 上移接口 + 两类实现 + 测试改用生产类（否则修完仍绿）。现场改一次点位就要重启进程，是这套系统最容易被绕过的一道工序。
5. **最后补能力与治理**（#10-13 #16-20）：位信号采集、`slave_id` schema、YAML 往返写、线程模型。

建议每修完一组，用一台真实 PLC + 一台 MQTT 网关做一次"拔网线 → 恢复"的现场演练：断线 5 分钟内应出现质量码降级与单设备报警，恢复后 1 个周期内自动回绿。这是当前代码最缺的验收口径。
