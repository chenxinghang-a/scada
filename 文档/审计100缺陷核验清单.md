### 判定为"不成立 / 口径分歧"的 3 项

| 编号 | 结论 |
|---|---|
| 013 | 报告称 64 位 BADC 应"字内字节交换"，但本项目 64 位 BADC 的既有约定是**字交换**（`tests/test_mc_fins_collector_adapter.py::_encode_float64` 与 `base_client` 编码侧一致）。按报告改会破坏与现网 BADC 设备的往返一致性，故保留原实现并在代码里写明口径。 |
| 057 | 报告称单设备健康度 `freshness` 恒 `unknown`。实测 `get_device_health()` 返回的是 `{device_id:register: {..., updated_at}}` 嵌套结构，`_freshness` 的 `isinstance(v, dict)` 能取到内层时间戳；只有"该设备没有任何评分"时才返回 unknown，语义正确。 |
| 075 | 报告称仿真初始化"先喂 120 点、后设 SPC 规格限"导致 Cp/Cpk 恒空。实测 `SPCAnalyzer.feed_data` 会自动补默认规格限（`_auto_set_spec_limits`），且能力指数是**读时惰性计算**（≥20 点即可），顺序不再影响结果。 |

## 五、机制性改进（round 372）—— 把"修过的坑"变成守卫

三条约束都是**可执行的测试**，不是文档承诺：

1. **工程量换算唯一入口** `core/engineering_units.py`（`to_raw` / `from_raw`）。
   行业里叫 tag scaling engine：一个点位一条换算通路，顺序固定。
   修复前仓库里有 10 份副本（智能层 2 份、采集层 5 份、网关 1 份、仿真 2 份），
   其中两份漏换算、一份双算。现由 `tests/test_engineering_units.py` 的 AST 守卫
   禁止生产代码再写 `raw*scale+offset` / `(value-offset)/scale`。
2. **动作结果统一判定** `core/action_result.py`（`is_failure`）。
   只有 `False` / `{'success': False}` 算失败，`None` 是"无结论"。
   修掉 `bool({'success': False}) == True` 导致的联锁"执行成功"假象
   （写入被拒 → `_interlock_states` 锁死 → 停机指令永不重试）。
3. **静默失效守卫扩展**（`tests/test_silent_exception_guard.py`）：
   参考 Ruff `B018 useless-expression` / pylint `W0104` 的思路，但**不用前缀**，
   而是显式列出项目内返回 bool/dict 的写/保存函数 —— 返回值被丢弃即红。
   前缀规则会把 `Path.write_text()` 等几十处正常用法抓进来，误报会让守卫失效。
4. **生命周期元测试** `tests/test_forget_device_coverage.py`：
   AST 反射找出所有被 `device_id`（含复合键）索引过的属性，与 `forget_device`
   实际清理集合比对，支持一层委托（`DataCollector → _forget_device_state`）。
   首次运行即发现三处漏清：`DeviceControlSafety._write_limits` /
   `_write_whitelist`、`PredictiveMaintenance.thresholds`，均已修复。

定向回归：`pytest` 采集/网关/时序/智能层 + 三个守卫共 **964 passed**。

## 六、并发快照审计（round 373）

主题：**运行期会被修改的字典，不得在锁外直接迭代**。

扫描口径（AST）：只抓 `for ... in self.<attr>.items():` 且该属性在 `__init__`
之外被下标赋值/del/pop/clear/update/setdefault/add/discard/remove 修改过。
初始化后不再变化的配置表、列表迭代（不会抛 RuntimeError）都不算。

修复的 12 处：

- `DeviceControlSafety`：`_interlock_rules`（批量控制/写入校验）、
  `_interlock_states`（写入警告）、`_device_health`（健康汇总）→ 锁内取快照；
- `MQTTClient._on_connect`：`_subscriptions` → 锁内快照（重连时订阅恢复一半）；
- `MQTTDataDistributor`：`_modules` 加锁快照；`_resubscribed_topics` 快照遍历；
- 五个网关的 `disconnect()`：`_clients` 改为「先摘链再遍历」，
  避免重连线程并发增删导致停网关抛 RuntimeError；
- `DeviceDataHub.write_point`：`set_point_override` 收进 `self._lock`，
  与 `_tick_once` 串行（否则 OPC UA/REST 写入撞上采样拍会 500）。

守卫：`tests/test_lock_discipline.py`。4 条豁免全部写明理由
（仿真器状态由 hub 锁串行、OPC UA 节点表只在 start 建、QueryBuilder 一次性对象）。

定向回归：设备控制/网关/MQTT/仿真/生命周期共 **392 passed**。

## 七、长跑稳定性（round 374）

主题：**后台线程静默死亡**与**无界历史**。

这类故障的共同点是"进程还活着、HTTP 还通、就是某个功能不再干活"，
而且线程异常不会传播到主线程，日志里最多一条 traceback。

修复 6 处：

- `core/connection_pool.py`：清理循环体加 try/except。`health_check` 是外部
  注入的回调（真实实现做 TCP/协议探测），它抛一次异常，回收线程就永久退出 ——
  空闲连接不再回收，`max_size` 被占满，新请求只能等超时。
- `模拟服务端/device_data_hub.py`：整个 tick 包 try。单设备 `update()` 已隔离，
  但快照整理/寄存器映射异常会让**所有设备同时冻住**。
- `采集层/simulated_client.py`：OPC UA / MQTT 推送循环加 try（一次数据生成
  异常不再冻住仿真数据）；`connect()` 不再无条件新建推送线程。
- `采集层/enhanced_simulated_client.py`：三处 `connect()` 同样改为
  "线程已在跑就不重复起"（重连循环会反复调 connect）。
- `core/fault_injection.py`：`_history` 上限 500。原来每次 inject/remove/clear
  都永久留一条 dict，演练脚本轮询时内存只涨不降。
- `采集层/recipe_simulator.py`：阶段历史上限 2000。原来只 append 不裁剪，
  24/7 产线每 30s 换阶段 → 每天 2880 条，一个季度几十万条。

新增守卫：

- `tests/test_background_loop_resilience.py`：AST 扫描 `loop/run/publish/
  listen/poll` 函数里的 `while`，循环体没有 `try` 即红。3 条豁免
  （定时任务体、蜂鸣器/闪灯）写明理由，且断言豁免必须仍命中。
- `tests/test_unbounded_history_round374.py`：两个历史上限的行为用例。

定向回归：连接池/故障注入/配方/模拟客户端 + 新守卫共 **175 + 134 passed**。
