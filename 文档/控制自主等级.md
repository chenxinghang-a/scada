# 控制自主等级：HITL / HOTL / HOOTL

> 设备控制权归属必须显式配置，不能靠“操作员碰巧在看屏幕”。

## 1. 三个等级

| 等级 | 配置值 | 含义 | 自动动作如何执行 |
|---|---|---|---|
| **HITL**<br>人在回路 / 环内 | `manual` | 人**必须**做决策、批准或修改 | 不直接执行，生成**待审批提案**；人批准/改值/驳回 |
| **HOTL**<br>人在回路上 / 环上 | `supervised` | 系统自动执行，人监督并可随时接管 | 人“武装”后直接执行；未武装时降级为待审批提案 |
| **HOOTL**<br>人在回路外 / 环外 | `automatic` | 全自动、无人值守 | 直接执行（安全联锁/量程/急停/审计仍然生效） |

关键区别：

- HITL 不是“拒绝自动写入”，而是**把自动写入变成人必须处理的提案**；
- HOTL 的“监督”是**可执行的授权**（武装/解除），不是口头要求；
- HOOTL 不等于“绕过安全”，急停、联锁、写白名单、回读验证一条不少。

## 2. 配置

```yaml
- id: press_line1
  name: 压机产线
  protocol: modbus_tcp
  host: 192.168.1.20
  port: 502
  device_class: actuator        # sensor/actuator/drive/meter/plc/relay/hmi/other
  electrical:                   # 铭牌参数（可选，展示/校验用）
    rated_voltage: 380
    rated_current: 32
    phases: 3
    power_type: ac
  autonomy: supervised          # manual / supervised / automatic
  registers: [...]
```

- 缺省 `autonomy: automatic`（保持既有行为，向后兼容）；
- 运行期可用 API 覆盖，**不写回配置文件**；配置文件是基线。

## 3. 工作流

### HITL（manual）

```
边缘决策/PID 想写 7  →  生成提案 action=ab12cd34（5 分钟有效）
   ↓ GET /api/control/pending-actions
人看到提案  →  approve（可传 value 改值）/ reject
   ↓
批准后以“人的身份”执行；执行结果写审计
```

同一设备+地址+类型的重复提案会**合并**（值取最新、`updates` 累加），
避免 PID 每个周期刷出几百条。

### HOTL（supervised）

```
POST /api/control/devices/<id>/autonomy/arm  {"minutes": 480}
   ↓
自动写入直接执行（审计记录“已武装 + 操作人”）
   ↓
POST .../autonomy/disarm   ← 人随时接管，之后的自动动作回到提案
```

武装到期自动失效，不存在“授权忘了收回”。

### HOOTL（automatic）

自动写入直接执行；人只通过看板/审计观察，不参与每次决策。

## 4. API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/control/devices/<id>/autonomy` | 当前等级、是否武装、剩余秒数 |
| POST | `/api/control/devices/<id>/autonomy` | 切换等级 `{mode, reason}`（engineer） |
| POST | `/api/control/devices/<id>/autonomy/arm` | 武装 `{minutes: 1~480}`（engineer） |
| POST | `/api/control/devices/<id>/autonomy/disarm` | 解除武装（engineer） |
| GET | `/api/control/pending-actions` | 待审批提案（可按 `device_id` 过滤） |
| POST | `/api/control/pending-actions/<action_id>/approve` | 批准，可带 `{value}` 修改 |
| POST | `/api/control/pending-actions/<action_id>/reject` | 驳回 `{reason}` |

## 5. 失败与审计

| 场景 | 行为 |
|---|---|
| 提案过期（默认 300s） | 自动作废并写审计 `pending_action_expired` |
| 提案超过 200 条 | 淘汰最老的 pending，写审计 |
| 人批准但设备未连接/联锁阻止 | 返回失败，动作不保留（下一轮自动逻辑会重新提案） |
| 自动来源但等级不允许 | 返回 `pending_approval: true`，**不是**错误刷屏 |
| 人工下发 | 永远放行这一层（仍受急停/联锁/量程约束） |

审计动作：`write_pending_approval`、`write_approved`、
`write_approval_failed`、`write_rejected`、`autonomy_mode_changed`、
`autonomy_armed`、`autonomy_disarmed`。

## 6. 选型建议

- **无人值守/黑灯产线**：`automatic`，但必须保证联锁规则、写白名单、
  急停回路独立有效；
- **有人值守产线**：`supervised`，交接班时武装，异常时一键解除；
- **调试/检修/首次上线**：`manual`，所有自动动作先过人；
- 不要把 `automatic` 当默认“省事”选项：它意味着人放弃逐次确认。
