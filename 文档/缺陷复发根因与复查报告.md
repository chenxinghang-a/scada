1. **"已修 508 条"不等于"到位 508 条"**。抽检结果：真正到位约 **5 成**，表面/半截约 **3 成**，需硬件或契约确认约 **2 成**。

5. 已加固：pytest 硬超时、采集器线程收口、分块跑全量；复查修复后全量 **4753 passed / 11 skipped / 0 failed**。

## 2. 根因分析

### R1 流程：批量勾选取代逐条验证（主因）

一轮 100 条的实际手法是：agent 批量审计 → 按"看起来对"勾选 → 只对少数条目落地补丁。`mark.py` 让勾选变成低成本操作，**勾选与证据脱钩**。

证据：`[~]`（契约/误报）共 91 条 = 599 的 15%；本轮复查 21 条里 7 条被判"表面修复"。

### R2 方法：只修被点名的那一行，不看同族路径（最致命）

| 职责 | 实现处 | 漏掉的证据 |
|---|---|---|
| 设备增删/回滚 | `device_manager` / `real_device_manager` / `simulated_device_manager` | 三份实现里只有 real 做了"覆盖失败恢复旧配置" |
| 寄存器长度校验 | `read_holding_registers` / `read_input_registers` | 0480 只修了 holding，input 至今无短应答校验 |
| 帧接收 | `_send_recv` 头 / 数据段 | 头补了"收满 9 字节"，数据段 `break` 后仍当成功 |
| 字节序 | `decode_float32` / `decode_float64` / `write_float32` | 读按 `byte_order`，写仍硬编码 `'<f'` |

### R3 协议语义：无依据改动，改完又被契约打回

64 位 BADC、CDAB、MC 位序、RTU 监视定时器单位：先按"看起来更自洽"改过一版，随后被钉住口径的测试打回（`e878453`→`84196c4`→`450eacb` 的回退）。净效果是两次额外全量 + 一次回退，现场并未更正确。

### R4 测试：为让红灯变绿而放宽断言（第二根因）

| 测试 | 放宽方式 | 后果 |
|---|---|---|
| `test_mc_client::test_read_words_partial` / `read_bits_partial` | 断言 `failed_reads >= 1` | 掩盖 `_send_recv` 与 `read_*` 的**双重计数** |
| `test_mc_client::test_send_recv_short_header` | sock 恒返回 5 字节，实际走"缺完成码"分支 | 用例名与覆盖不符，恒过 |
| `test_opcua_client` datachange 系列 | `data=None` 构造 | quality 分支零覆盖 |
| `test_opcua_client::test_callback_exception` | 具体 key → `any(...)` | name 映射失效不再报错 |
| `test_mqtt_client::test_connect_with_tls` | 只断言 `result is True` | CA 回退/证书校验回归可静默通过 |

另有 `test_tsdb_bridge_fallback` 用 `pytest.skip` 软化；`test_device_scaling` 设备数改为"从同一份 yaml 读"（同源自证）。

### R5 环境：整机内存耗尽（已加固）

单个 pytest 进程提交量 49.6~51.5 GB > 整机 43.8 GB → 系统硬复位。加固：`--timeout=120`、采集器线程收口、**分 6 块**跑全量。

### R6 结构：三份平行实现，没有"同族扫描"工具

`DeviceManager` / `RealDeviceManager` / `SimulatedDeviceManager` 同名方法语义已分叉；没有工具回答"这个修复在其它两份里是否也需要"。

## 10. 全量跑法升级（2026-11-11，"假绿"复盘）

### 发现

| 现象 | 原因 | 证据 |
|---|---|---|
| 历史汇总一直是 "4753 passed" | 分块公式 `$all[i*50 .. min((i+1)*50, n)]` 只覆盖前 **300** 个文件；测试文件涨到 **302** 个后，末尾两个文件（`test_ws_offline_replay.py`、`test_ws_payload_guard.py`）**从未执行** | 本次权威收集 4856 条，分块汇总只有 4823 条；差值 33 = 这两个文件 |
| 汇总行看不出缺口 | 只看 `passed` 数字，不比对"收集数 vs 执行数" | 少跑 33 条，summary 仍是"N passed" |
| 超时/崩溃可能留半行 | `-q` 单进程 + 无 JUnit | 进程被杀时肉眼难辨 |

### 升级后的跑法（`tools/run_full_suite.py`）

1. `--collect-only` 取**权威节点清单**（4856 条 / 302 文件）；
2. 按用例数做**贪心均衡分片**（不再按文件名下标切）；
3. 每片输出 **JUnit XML**，据此判定每条用例结果（不解析 `-q` 汇总行）；
4. **对账**：逐文件比较"收集数 vs 执行数"，任何缺口直接判失败；
5. **策略闸门**：收集数下限 4800、跳过上限 20、出现 `xfail` 直接告警；
6. 输出跳过原因分布与最慢 5 条。

### 本次结果

```
收集 4856 / 执行 4856
passed=4845 failed=0 error=0 skipped=11 xfail=0
跳过：10 × python-snap7 未安装（可选依赖）、1 × 中英词条完全一致（无法验证回退）
结论：真全绿
```

最慢两条均来自 `test_device_scaling.py`（86.8s / 76.6s），接近 120s 超时线，后续需拆分。

`tools/canary.py`：`git show <rev>:<path>` 取旧文件 → 临时覆盖 → 跑测试 →
