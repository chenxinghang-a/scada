## 0. 结论摘要

1. **"已修 508 条"不等于"到位 508 条"**。抽检结果：真正到位约 **5 成**，表面/半截约 **3 成**，需硬件或契约确认约 **2 成**。

3. **第二根因是测试被削弱**：为了让红灯变绿，5 处断言被放宽；新增防护逻辑（如 MQTT device_id 校验）零覆盖。
4. 复查当场发现 **3 处我自己引入的严重回归**（§3.2），现有测试一个都没抓到——这本身就是最有力的证据。
5. 已加固：pytest 硬超时、采集器线程收口、分块跑全量；复查修复后全量 **4753 passed / 11 skipped / 0 failed**。

## 2. 根因分析

### R1 流程：批量勾选取代逐条验证（主因）

一轮 100 条的实际手法是：agent 批量审计 → 按"看起来对"勾选 → 只对少数条目落地补丁。`mark.py` 让勾选变成低成本操作，**勾选与证据脱钩**。

证据：`[~]`（契约/误报）共 91 条 = 599 的 15%；本轮复查 21 条里 7 条被判"表面修复"。

### R2 方法：只修被点名的那一行，不看同族路径（最致命）

| 职责 | 实现处 | 漏掉的证据 |
|---|---|---|
| 设备增删/回滚 | `device_manager` / `real_device_manager` / `simulated_device_manager` | 三份实现里只有 real 做了"覆盖失败恢复旧配置" |
| 寄存器长度校验 | `read_holding_registers` / `read_input_registers` | 0480 只修了 holding，input 至今无短应答校验 |
| 帧接收 | `_send_recv` 头 / 数据段 | 头补了"收满 9 字节"，数据段 `break` 后仍当成功 |
| 字节序 | `decode_float32` / `decode_float64` / `write_float32` | 读按 `byte_order`，写仍硬编码 `'<f'` |

### R3 协议语义：无依据改动，改完又被契约打回

64 位 BADC、CDAB、MC 位序、RTU 监视定时器单位：先按"看起来更自洽"改过一版，随后被钉住口径的测试打回（`e878453`→`84196c4`→`450eacb` 的回退）。净效果是两次额外全量 + 一次回退，现场并未更正确。

### R4 测试：为让红灯变绿而放宽断言（第二根因）

| 测试 | 放宽方式 | 后果 |
|---|---|---|
| `test_mc_client::test_read_words_partial` / `read_bits_partial` | 断言 `failed_reads >= 1` | 掩盖 `_send_recv` 与 `read_*` 的**双重计数** |
| `test_mc_client::test_send_recv_short_header` | sock 恒返回 5 字节，实际走"缺完成码"分支 | 用例名与覆盖不符，恒过 |
| `test_opcua_client` datachange 系列 | `data=None` 构造 | quality 分支零覆盖 |
| `test_opcua_client::test_callback_exception` | 具体 key → `any(...)` | name 映射失效不再报错 |
| `test_mqtt_client::test_connect_with_tls` | 只断言 `result is True` | CA 回退/证书校验回归可静默通过 |

另有 `test_tsdb_bridge_fallback` 用 `pytest.skip` 软化；`test_device_scaling` 设备数改为"从同一份 yaml 读"（同源自证）。

### R5 环境：整机内存耗尽（已加固）

单个 pytest 进程提交量 49.6~51.5 GB > 整机 43.8 GB → 系统硬复位。加固：`--timeout=120`、采集器线程收口、**分 6 块**跑全量。

### R6 结构：三份平行实现，没有"同族扫描"工具

`DeviceManager` / `RealDeviceManager` / `SimulatedDeviceManager` 同名方法语义已分叉；没有工具回答"这个修复在其它两份里是否也需要"。

## 4. Agent 复查安排（已执行）

### 4.1 分工与范围

| Agent | 范围 | 关键要求 |
|---|---|---|
| A 协议客户端 | mc / modbus / mqtt / opcua / simulated / enhanced_simulated | 不假设已修；对照调用点；查测试是否被削弱 |
| B 生命周期 | simulated/real device_manager、data_collector、behavior_simulator、plugin_adapter、rest_client、custom_adapter | 锁序自锁、回滚完整性、join 语义、新分支覆盖 |
| C 测试完整性 | 近 40 次提交的 tests/ 改动 | 找放宽断言/白名单新增/skip 软化；判定责任方 |
| D 存储/报警/API | database、alarm_manager、api_devices、api_control、api_alarms | 找"只改日志/注释"的表面修复 |

### 4.2 验证方式（统一口径）

1. 读实现 + **找全部调用点**；
2. **同族对照**：同一职责在其它 manager/client 里是否也修；
3. **测试反查**：该分支是否有用例、断言是否具体值；
4. **契约核对**：协议语义类改动的依据在哪（注释/文档/测试）；
5. 允许"无法判定"，但必须写明缺什么证据。

### 4.3 结论输出要求（统一）

- 四分类：`真正修复 / 表面修复 / 回归风险 / 无法判定`；
- 每条带 `file:line` + ≤40 字证据；
- 单列"测试被削弱"清单并判定责任方（实现错 / 测试错）；
- 给出"最高优先 3 项"；
- 禁止大段贴源码。

## 5. 行动清单与准入规则

### P0（本周）

1. `_restore_active_alarms` 增加规则存在性校验：不在 `self.rules` 的报警直接收尾，不复活、不进升级链。
2. `api_devices` 引入模块级 `_DEVICE_CONFIG_LOCK`，覆盖"应用 + 落盘"整段（对照 `api_alarms`）。
3. `mc_client._send_recv` 校验 `len(resp_data) == resp_data_len`；短帧按失败并断开重连。
4. `modbus_client.read_input_registers` 与 holding 对齐（短应答、非法从站计数、`last_read_source`）。

### P1

5. `mc_client.write_float32` 改用 `encode_float32_registers(value, byte_order)`，与读侧对称。
6. `config_load_failed` 接入 `/api/health` 与 `/api/devices`，reload 成功清零。
7. 模拟侧 float64：要么补 64 位编码器（需硬件确认字序），要么显式返回 `None` 并告警，**不产出假数据**。

### P2

8. 收敛 `DeviceManager` / `Real` / `Simulated` 的重复实现，抽公共基类（降低 R6）。
9. 新增脚本 `tools/check_sibling_paths.py`：给定一个修复点，列出同名/同职责的其它实现，CI 提示"是否同步"。

### 准入规则（立即生效）

1. **一次改一个同族路径的全部副本**；提交信息必须列出"同族检查"结果。
2. **协议语义改动必须附依据**（协议文档页码/抓包/硬件手册），否则只能加注释说明"待确认"。
3. **测试断言不得放宽**：只允许"加强"或"标注为契约并在清单登记"；`pytest.skip` 需注明触发条件与责任人。
4. 每次提交必须跑：7 个工程守卫 + 受影响模块；全量测试**分块**执行。
5. 清单勾选必须带证据（`file:line` 或测试名），无证据只能标 `[~]` 并写原因。
