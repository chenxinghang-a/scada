# 质量码口径

> 本文把「代码里怎么判、库里怎么存、前端怎么画」三处的质量码口径写成一份可审阅的表。
> 目的是让现场只需**确认**口径，而不是从头翻代码。
> 对应的追溯条目：`文档/安全功能追溯.yaml` 的 SF-02。

实现位置：`采集层/data_collector.py::DataQualityAssessor`（枚举 + 判定）、
`core/data_quality.py`（如有跨模块引用以本文件为准）、
`静态资源/js/dashboard.js::getQualityColor`（前端映射）。

---

## 1. 实际会产生的 5 个码

码值同时是 OPC UA StatusCode 的低 8 位简化表示（本项目只用到下面这些）。

| 码 | 值 | 含义 | 触发条件（判定顺序见 §2） |
|---|---|---|---|
| `GOOD` | **192** (0xC0) | 好 | 通过全部检查 |
| `UNCERTAIN_LAST_USABLE` | **64** (0x40) | 最后可用值 | ① 客户端缓存兜底（`last_read_source == 'cache'`）且原判为 GOOD；② 值长时间不变（卡死窗口，`SENSOR_STUCK_WINDOW_S`） |
| `BAD` | **0** (0x00) | 坏 | 值为 `None` / `NaN` / 非数值类型 |
| `BAD_SENSOR_FAILURE` | **4** (0x04) | 传感器故障 | 设备 `status == 'fault'`；或值为 ±Inf；或 `abs(value) > 1e10` |
| `BAD_COMM_FAILURE` | **6** (0x06) | 通信故障 | 设备 `status ∈ {'offline', 'disconnected'}` |

## 2. 判定优先级（顺序即语义，不能调）

`DataQualityAssessor.assess()` 依次判断，**先命中先返回**：

```
1. device_status ∈ {offline, disconnected}  → BAD_COMM_FAILURE(6)
2. device_status == fault                   → BAD_SENSOR_FAILURE(4)
3. value 为 None / NaN / 非数值              → BAD(0)
4. value 非有限（±Inf）                      → BAD_SENSOR_FAILURE(4)
5. |value| > 1e10                           → BAD_SENSOR_FAILURE(4)
6. 值长时间不变（> SENSOR_STUCK_WINDOW_S）    → UNCERTAIN_LAST_USABLE(64)
7. 其余                                      → GOOD(192)
```

**为什么顺序重要**：

- 1 在 3 之前：设备已经离线时，即便这一条的值看起来正常，也必须报通信故障 ——
  否则「设备死了但最后一个值很合理」会一直是 GOOD。
- 采集层还有一层补充（在 `assess()` 之后）：
  ```python
  if data.get('stale') and quality == GOOD:
      quality = UNCERTAIN_LAST_USABLE
  ```
  注意条件是 `== GOOD`：**已判 BAD 的值不会被"升级"成 UNCERTAIN**。
  设备真离线时保住 6，而不是被缓存的 stale 标记降级成 64。

## 3. 定义了但**从不产生**的 3 个码

这三个枚举值存在，但全仓库非测试代码零引用（`grep DataQualityAssessor.<X>` 为空）：

| 码 | 值 | 说明 |
|---|---|---|
| `UNCERTAIN` | 104 (0x68) | 通用"不确定"，没有判定分支 |
| `UNCERTAIN_SENSOR_CAL` | 80 (0x50) | 需校准，没有判定分支 |
| `BAD_OUT_OF_SERVICE` | 8 (0x08) | 停用，没有判定分支 |

**这不是缺陷**，但有两层影响需要知道：

1. 前端 `getQualityColor()` 用的是**阈值分档**（`>=192` 绿 / `>=64` 黄 / 其余红），
   所以 104 / 80 若将来出现会显示黄色、8 显示红色 —— 映射本身是对的。
2. 如果有人按「OPC UA 有 8 种码」去写报表或对接上位机，会以为这 8 种都可能出现。
   实际只有 §1 的 5 种。

> 若现场需要区分「停用」与「故障」，或需要「需校准」，
> 需要在 `assess()` 里加判定分支并给出数据来源（例如设备配置项），
> 不能只加枚举。

## 4. 存储与接口

| 环节 | 形态 | 说明 |
|---|---|---|
| 采集层内部（队列 item） | `data['quality'] = <int>` | 未评估前没有该字段 |
| 数据库 `realtime_data.quality` | `INTEGER DEFAULT 192` | **0 是合法的 BAD，不是"缺失"** |
| `GET /api/data/realtime` | `quality: <int>` | 原样返回整数，不做字符串化 |
| `GET /api/data/history` | 聚合后的样本 | 聚合时质量码的取舍见 `存储层/database.py` |

### ⚠️ 入库的"乐观默认"（需要现场确认）

`insert_data_batch` 对每一行做：

```python
q = d.get('quality', 192)            # 缺字段 → 192
# 非数值（字符串/None）→ warning 后仍按 192 落库
```

也就是说：**采集层没算质量码（或算出个不能转 int 的东西）时，落库结果是 GOOD**，
只留一条 warning。

这与本仓库其它地方的口径**正好相反**：短帧/坏帧一律丢弃、绝不补值；
而这里缺质量码却补成"合格"。

为什么先不改：`test_realtime_quality_persistence::test_missing_quality_defaults_to_good`
把这个行为钉住了，说明它是**有意为之**（很可能是为了兼容不带 quality 的
旧调用方/旧数据）。改成 fail-closed 会让那些路径的历史数据全变红，
影响面比"多一条 warning"大。

**建议的处置**：现场确认是否还有调用方不带 quality。
确认没有之后，把它改成"缺 quality 拒绝入库 + 计数"，
再同步改那条测试（不是删掉，是把断言反过来并写明依据）。

### 关于 `quality = 0`

`0` 是一个**合法的 BAD 码**，不是"没填"。任何地方用 `if not quality` 判断缺失
都会把 BAD 当成缺失 —— 必须用 `is None`。`test_realtime_quality_persistence`
里有专门的 `test_bad_zero_is_not_treated_as_missing` 钉这条。

## 5. 待现场确认（SF-02 的核心）

下面四条必须与上位机 / 报表口径对齐后才能把 SF-02 从 partial 升到 verified：

1. **「不确定」的语义边界**
   本系统把「缓存兜底」和「值长时间不变」都归到 64（UNCERTAIN_LAST_USABLE）。
   有些上位机把这两种拆成不同码（一个是通信类、一个是设备类）。
   现场报表如果按"不确定=设备可疑"统计，口径会不一致。

2. **卡死窗口的取值**
   `SENSOR_STUCK_WINDOW_S = 300`（5 分钟），硬编码常量，并且判据是
   `abs(value - last_value) < 0.001` —— 变化小于千分之一就算"没变"。
   采样周期 60s 的设备用 5 分钟窗口会频繁误判；
   而量程很大的模拟量（如 0~1e6）千分之一的阈值又太松。
   现场需要按设备类型分别配置，还是全局一个值？

3. **BAD 是否要参与报警**
   现在 BAD 只影响质量码，不直接触发报警（报警走 `alarm_manager` 的阈值规则）。
   有些现场要求「连续 N 个 BAD 就报通信中断」。这条属于报警策略，需明确。

4. **入库的"缺 quality 默认 GOOD"**
   见 §4 的说明。需要确认是否还有调用方不带 quality，
   确认后应改为 fail-closed。

## 附：与 OPC UA StatusCode 的对应

本项目只借用 StatusCode 的**低位部分**做简化表示，不是完整的 OPC UA 质量体系
（没有 SubStatus、没有 InfoBits、没有 SymbolicId）。

如果需要与真正的 OPC UA 客户端互通，需要做一层映射：
`192 → 0x00 (Good)`、`64 → 0x40 (UncertainLastUsable)`、
`4 → 0x04 (BadSensorFailure)`、`6 → 0x06 (BadCommunicationError)`、
`0 → 0x00 (Bad)` —— 注意 **192 与 0 的 OPC UA 高位不同**，不能直接当 StatusCode 传。
